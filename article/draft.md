## はじめに

ブロックチェーンで送金するには、送金額とは別にガス代が必要になる。ガス代はそのチェーンの基軸通貨（Ethereum では ETH）で支払う。そのため、USDC[^usdc]を100ドル分持っていても、ETH を持っていなければ USDC を送金できない。

この制約を回避する方法として、署名で送金を承認し、ガス代は別の者が支払う方式が提案されてきた。メタトランザクション、EIP-2612、EIP-3009、Permit2 がその例である。x402 はこの系統に属するプロトコルで、HTTP の`402 Payment Required`を使い、API 呼び出しの際にステーブルコインで支払う。AI エージェントが自律的に支払うための仕組みとして紹介されることが多い。

本稿の出発点は次の疑問である。ガス代を持たずに支払えることは、決済における主要な課題なのか。カード決済や銀行振込には、もともとガス代に相当する負担がない。ブロックチェーン固有の制約をブロックチェーン上の技術で解消しても、それが決済一般の課題の解決になるとは限らない。

本稿では、この疑問を実装と実験で検討する。x402 の公式 SDK と、Circle が公開している USDC の実装をローカルのブロックチェーン上で動かし、まず正常な支払いを1件成立させる。次に、署名の失効、応答の喪失、同時リクエストといった失敗条件を加えて挙動を観察する。最後に、AI エージェントに持たせるウォレットを設計し、どの制約をどの層で強制できるかを調べる。

検討の軸は次の三つの区別である。

- 署名が正しいこと
- 送金が成立すること
- 購入が適切に成立すること

コードとログはすべて公開している（https://github.com/avcdsld/x402-techbook-lab）。本文には、挙動の違いに関係する部分だけを抜粋する。

[^usdc]: 米ドルと価格が連動するように設計されたトークン（ステーブルコイン）の一つ。Circle 社が発行する。銀行預金そのものではない。

## 1. x402とは何か

### HTTP 402 ステータスコード

HTTP の`402 Payment Required`は、RFC 9110 §15.5.3 で「将来の使用のために予約」とされているステータスコードである。x402 はこのコードを使った支払いの手順を定める。流れは次のとおりである。

```
クライアント                       リソースサーバー                facilitator
    │ GET /report                        │                               │
    │──────────────────────────────────▶│                               │
    │ 402  PAYMENT-REQUIRED: 支払い条件    │                               │
    │◀──────────────────────────────────│                               │
    │ （署名を作る）                       │                               │
    │ GET /report                        │                               │
    │ PAYMENT-SIGNATURE: 署名付きの支払い   │                               │
    │──────────────────────────────────▶│ verify ─────────────────────▶│
    │                                    │ settle ─────────────────────▶│──▶ ブロックチェーン
    │ 200  PAYMENT-RESPONSE: 決済結果      │                               │
    │◀──────────────────────────────────│                               │
```

構成要素は三つである。

- クライアント：買い手。支払い条件を読み、署名を作る。
- リソースサーバー：売り手。API そのもの。
- facilitator：署名を検証し（`verify`）、ブロックチェーンへ送金トランザクションを送る（`settle`）[^facilitator]。ガス代は facilitator が支払う。

支払い条件は、ネットワーク（例：Base）、トークン（例：USDC）、金額（例：10000＝0.01 USDC）、宛先アドレス、署名の有効期間（例：60秒）などを含む JSON で、base64 に変換してヘッダーに載せる。

[^facilitator]: リソースサーバーが facilitator を兼ねてもよい。仕様上は HTTP API として定義されている。

### EIP-3009 による署名送金

EVM 系チェーンで x402 が既定で使う送金方式は、EIP-3009 の`transferWithAuthorization`である[^eip3009]。買い手は次の6項目に EIP-712 形式で署名する。

```
TransferWithAuthorization(
  address from, address to, uint256 value,
  uint256 validAfter, uint256 validBefore, bytes32 nonce
)
```

この署名を保持する者は誰でも、トークンコントラクトに署名内容どおりの送金を実行させることができる。ガス代は実行した者が負担し、署名者は負担しない。署名に宛先と金額が含まれるため、facilitator はそれらを変更できない。`nonce`[^nonce]は一度使用すると再使用できないため、同じ署名で2回送金することはできない。

仕様（`scheme_exact_evm.md`）は facilitator の検証手順として、署名の検証、残高の確認、金額と有効期間の確認、トークンとネットワークの一致の確認、送金のシミュレーションを挙げている。

[^eip3009]: ERC-20 トークンに署名による送金を追加する規格。USDC が実装している。x402 は他に Permit2、ERC-7710 による方式も定義しているが、本稿では扱わない。
[^nonce]: 署名付きの操作を一度きりにするための識別値。EIP-3009 では32バイトの乱数を使う。

### 仕様における AI エージェントの扱い

x402 の仕様書の「AI Agent Integration」の節は、エージェントが自律的にリソースへ支払えることなどを挙げている。予算管理と支出制御については、次のように実装に委ねている。

## 2. まず支払ってみる

### 実験環境

失敗条件を加える前に、正常な支払いを1件成立させる。

| 部品 | 使ったもの |
| --- | --- |
| ブロックチェーン | anvil（Foundry のローカル EVM） |
| トークン | Circle の `stablecoin-evm` に含まれる FiatTokenV2_2（USDC の実装）をソースからコンパイル |
| x402 | 公式 SDK `@x402/core` `evm` `express` `fetch` 2.28.0（変更なし） |

USDC はプロキシを介さず、実装コントラクトを直接デプロイした。送金と署名検証のロジックは本番と同じソースである。facilitator は公式の`x402Facilitator`をリソースサーバーと同じプロセスで呼び出している。間には、ログ出力と故障注入のための層だけを挟んだ。

### 売り手と買い手のコード

売り手側は、ルートごとに支払い条件を設定する。

```ts
app.use(paymentMiddleware({
  "GET /report": {
    accepts: [{
      scheme: "exact",
      network: "eip155:31337",
      payTo: seller,
      price: { amount: "10000", asset: usdc, extra: { name: "USD Coin", version: "2" } },
      maxTimeoutSeconds: 120,
    }],
  },
}, resourceServer));

app.get("/report", (req, res) => res.json({ report: "..." }));
```

買い手側は`fetch`をラップする。

```ts
const client = new x402Client().register("eip155:*", new ExactEvmScheme(buyer));
const payFetch = wrapFetchWithPayment(fetch, client);
const res = await payFetch(`${url}/report`);
```

### 正常系の結果

実行時のログは次のとおりである（抜粋）。

```
[186ms] server       ← GET /report               (支払いなし)
[189ms] server       → HTTP 402
[198ms] client       署名を作成 nonce=0x241b…  value=10000
[200ms] server       ← GET /report               (支払いあり)
[213ms] facilitator  verify  isValid=true
[214ms] server       handler 実行
[230ms] facilitator  settle  success=true tx=0x02ea…
[231ms] server       → HTTP 200
```

買い手の残高は 0.01 USDC 減り、売り手の残高は 0.01 USDC 増えた。nonce は使用済みになり、トランザクションの送信者は facilitator だった。後の実験では、ETH の残高が0のコントラクトウォレットからも支払えた。この範囲では、買い手が ETH を持たずに支払えることを確認できた。

ログでは、`handler 実行`が`settle`より前に記録されている。公式の Express ミドルウェアは、検証が通ると API の処理を実行し、その応答を送信せずに保持する。決済が確定した後に応答を送信し、決済が失敗した場合は保持した応答を破棄して 402 を返す。

したがって、サービスの処理は送金の確定より前に実行される。本文は返さないため、買い手が支払わずに結果を得ることはない。一方で、計算資源は消費され、外部の API を呼び出していればその費用も発生する。

また、最初の実行では、402 を受け取った直後にクライアント側でエラーになった。

```
All payment requirements were rejected by spendControls: only default assets
or entries in spendControls.allowedAssets are allowed.
```

SDK のクライアントは既定で、SDK に登録されていないトークンへの支払いを拒否する。ローカルにデプロイした USDC は登録されていないため、許可リストに追加した。この支出制御については第4章で扱う。

次章では、verify と settle の間に状態が変化した場合の挙動を調べる。

## 3. 決済を壊してみる

### 3.1 署名は正しいのに、支払えない

#### 状態に依存する署名

EOA[^eoa]の署名は暗号学的に検証できる。署名とメッセージから署名者が一意に決まり、その結果は時間が経っても変わらない。

スマートウォレット（コントラクトで実装されたウォレット）は秘密鍵を持たない。そのため EIP-1271[^1271]では、ウォレットのコントラクト自身が署名の有効性を返す。以下は実験用ウォレットの関数部分である。

```solidity
function isValidSignature(bytes32 hash, bytes calldata sig) external view returns (bytes4) {
    return _recover(hash, sig) == owner ? MAGIC : INVALID;
}

function rotateOwner(address next) external {
    require(msg.sender == owner, "not owner");
    owner = next;
}
```

署名が有効かどうかは、その時点の owner が署名したかどうかで決まる。owner を変更（鍵をローテーション）すると、過去に作成した署名はすべて無効になる。

この性質は USDC の実装でも言及されている。署名検証ライブラリのコメントは次のとおりである。

> NOTE: Unlike ECDSA signatures, contract signatures are revocable, and the outcome of this function can thus change through time. It could return true at block N and false at block N+1 (or the opposite).
> （`contracts/util/SignatureChecker.sol`）

x402 では verify と settle の間に、少なくとも API の実行時間分の間隔がある。

[^eoa]: Externally Owned Account。秘密鍵で直接操作する、通常の Ethereum アカウント。
[^1271]: スマートコントラクトが、署名の有効性を問い合わせに応じて返すための規格。

#### 実験

facilitator の`settle`の直前にフックを挟み、そこで署名を失効させた。比較のため、EOA でも同様の操作を行った。EOA では、EIP-3009 に定義されている`cancelAuthorization`（nonce を先に使用済みにする操作）を使った。

| ケース | HTTP | API実行 | 送金 | facilitator の tx | facilitator のガス代 |
| --- | --- | --- | --- | --- | --- |
| A 1271・何もしない | 200 | 1 | 0.01 | 1 | 0.000101 ETH |
| B 1271・verify後に owner 交代 | 402 | 1 | 0 | 0 | 0 |
| C EOA・verify後に `cancelAuthorization` | 402 | 1 | 0 | 0 | 0 |
| D 1271・settle の tx 送信後に owner 交代 | 402 | 1 | 0 | 1（失敗） | 0.000052 ETH |
| E EOA・settle の tx 送信後に `cancelAuthorization` | 402 | 1 | 0 | 1（失敗） | 0.000034 ETH |

（ガス代は anvil 上の値で、比較のためにのみ示す）

B は、SDK が`settle`の前に署名を再検証した時点で止まった。SDK の検証は、コードを持つアドレスに対してはオンチェーンの`isValidSignature`を呼び出す。トランザクションは送信されず、facilitator の費用は発生していない。

C を止めたのは SDK の明示的な検査ではない。`settle`前の再検証では、送金のシミュレーションは既定で無効になっている（`simulateInSettle: false`）。C を止めたのは、viem（Ethereum クライアントライブラリ）がトランザクションの送信前に行うガス見積りである。見積りの段階で送金が revert することが判明し、送信が中止された。

D と E は、facilitator がトランザクションを送信した後に、より高い手数料を付けた失効のトランザクションを送信したケースである。採掘されたブロックでは、失効のトランザクションが先、送金のトランザクションが後に並んだ。

```
[834ms] facilitator  settle tx を送信 0xdd5d…
[839ms] wallet       より高いチップで owner 交代 tx を投入
[856ms] chain        1ブロック採掘 order=[owner交代, settle]
[858ms] facilitator  settle success=false reason=transaction_failed
```

送金は revert し、facilitator はガス代のみを支払った。

#### 結果の解釈

この現象は EIP-1271 に固有ではない。EOA でも`cancelAuthorization`（C・E）や、残高を別のアドレスへ移す操作で同じ状態になる。原因は、検証と実行が別の時刻に行われることにある。

EIP-1271 の場合、失効は鍵のローテーションのような通常の運用操作によっても起きる。ローテーションを行うと、未決済の支払いはすべて無効になる。

D と E で利益を得た者はいない。買い手は本文を受け取っていない。費用を負担したのは、API を実行した売り手（計算資源）と、ガス代を支払った facilitator である。この操作を攻撃とみなす場合、その内容は、買い手が自分の支払いを取り消すことで売り手と facilitator に費用を負わせるものになる。x402 の仕様は ERC-7710 方式の節で、この競合を facilitator のリスクとして記載している。EIP-3009 方式の節には同様の記載はないが、今回の実験では EIP-3009 でも同じ現象が起きた。

verify を通過した支払いが、settle の時点でも実行可能である保証はない。サービスを先に実行する構成では、verify から settle までの間に生じる失敗のリスクを売り手が負う。

### 3.2 同じものに二度払う

#### GET の安全性・冪等性と支払い

HTTP の GET は安全なメソッドと定義されている（RFC 9110 §9.2.1）。これは、クライアントがサーバーの状態変更を要求しないという意味である。また GET は冪等であり、同じリクエストを複数回送っても、意図される効果は1回の場合と同じである。そのため、ブラウザや HTTP ライブラリは、通信が切断された GET を再送することがある。

x402 では、GET の処理の中で送金が行われる。

対象とする状況は次のとおりである。買い手が支払い、送金はブロックチェーン上で確定した。その直後に通信が切断され、成功応答が買い手に届かなかった。この場合、買い手は支払いが成立したかどうかを応答から判断できない。

この状況を再現するため、settle が成功した後、応答を送信する時点で TCP 接続を切断した。

```ts
res.end = (...args) => {
  if (dropResponse.on && res.statusCode === 200) {
    dropResponse.on = false;
    req.socket.destroy();   // settle 成功後の応答を送らずに接続を切る
    return res;
  }
  return end(...args);
};
```

#### 実験

A〜F では、最初の決済の直後に応答を1回だけ破棄した。G・I では応答を破棄せず、同じ購入のリクエストを同時に2件送った。

| | 重複防止 | 再試行のしかた | 最終応答 | 支払い | API実行 |
| --- | --- | --- | --- | --- | --- |
| A | なし | SDK で再リクエスト | 200 | 2 | 2 |
| B | なし | 同じ署名を再送 | 402 | 1 | 1 |
| C | `payment-identifier` | 同じ署名を再送 | 200 | 1 | 1 |
| D | `payment-identifier` | 同じ id で SDK 再リクエスト | 409 | 1 | 1 |
| D2 | 〃 | D の後、拒否された署名を売り手が実行 | — | 2 | 1 |
| E | `payment-identifier` | 再起動して id も作り直す | 200 | 2 | 2 |
| F | アプリの購入 ID | 再起動して同じ購入 ID で再リクエスト | 200 | 1 | 1 |
| G | アプリの購入 ID | 同時に2件 | 200/200 | 2 | 2 |
| I | 購入 ID ＋処理中の予約 | 同時に2件 | 409/200 | 1 | 1 |

各ケースの結果は次のとおりである。

A（SDK で再リクエスト）：サーバーは再び 402 を返し、SDK は新しい nonce で新しい署名を作成する。新しい署名は別の送金として処理されるため、nonce による重複防止は働かず、支払いは2回になった。

B（同じ署名を再送）：nonce が使用済みのため検証で失敗し、402 が返った。二重払いは発生しないが、買い手は結果を受け取れない。

nonce が防ぐのは同じ署名の再利用であり、同じ購入の繰り返しではない。署名の同一性と購入の同一性は別の概念である。

C・D（公式の冪等性拡張）：x402 には`payment-identifier`という拡張がある。クライアントが支払いに ID を付け、再試行では同じ ID を使う。SDK が提供するのは ID の宣言と抽出の関数のみで、重複を判定する処理は実装者に任されている。SDK のソースには次のコメントがある。

```ts
// No enrichment needed - the declaration is static
// Future hooks for idempotency could be added here if needed
```

公式のサンプルサーバーは、ID と、署名を含むペイロード全体の指紋（ハッシュ）を記録する。同じ署名で再送すると、記録済みの結果を返す（C）。同じ ID で新しい署名を送ると、同じ ID で内容が異なるものとして 409 を返す（D）。D では二重払いは発生しないが、買い手は結果を受け取れない。

D2（409 で拒否された署名）：D で 409 が返されたリクエストにも署名が含まれていた。この署名は未使用であり、有効期限（`validBefore`）まで有効である。売り手側でこの署名を`transferWithAuthorization`に渡すと、送金は成功した。署名付きの送金承認は、受け取った者が有効期限内であればいつでも実行できる。サーバーが 409 で拒否しても、署名はサーバー側に残る。有効期限は、サーバーが支払い条件の`maxTimeoutSeconds`で指定する。

F（アプリの購入 ID）：支払いの処理より前に、アプリ側の購入 ID（例：注文番号）を認証済みの買い手と結びつけて照合する。購入済みであれば、支払いを求めずに記録済みの結果を返す。この方式では、クライアントが再起動して署名を作り直しても、支払いは1回だった。購入の同一性は、アプリケーション層で扱う必要がある。

G・I（同時リクエスト）：F の実装では、同じ購入 ID のリクエストが同時に2件届くと、両方が未購入と判定されて処理が進み、支払いが2回になった（G）。処理中の購入 ID を予約し、2件目に 409 を返すようにすると、支払いは1回になった（I）。

ただし I でも、409 を受けた側のクライアントは、402 を受け取った時点で署名を作成していた。x402 の手順では、署名の作成はサーバーが支払い付きのリクエストを受け取るより前に行われるため、サーバー側の予約より先に署名が存在する。

#### 従来の決済 API との共通点と相違点

G と I で起きた問題は、従来の決済 API でも同様に起きる。Stripe などの決済 API は、`Idempotency-Key`ヘッダーで再試行を識別する仕組みを提供している[要確認：Stripe の idempotency key の仕様、同時リクエスト時の挙動]。応答が失われた場合に支払いの成否を確認し、購入を1回に限定する処理は、決済手段にかかわらずアプリケーション側の責任である。

ブロックチェーン固有の要素は D2 である。支払いを実行する能力が決済事業者ではなく署名自体にあるため、拒否されたリクエストに含まれていた署名が、実行可能な状態で残る。

あわせて観察された現象を記録する。素の viem でトランザクションを送信する facilitator（公式の facilitator サンプルと同じ構成）は、2件の`settle`を同時に処理すると、送信アカウントの nonce が衝突した（`nonce too low`）。この実験ではその結果として二重払いは発生しなかったが、API は2回実行され、片方の買い手には 402 が返った。facilitator は単一のアカウントからトランザクションを送信するため、並行処理には nonce の管理が必要になる。

## 4. AIの財布を設計する

### 支払いの可否を判断する層

x402 は支払いの手順を定めるが、AI エージェントが支払ってよいかどうかの判断は定めていない。仕様が実装に委ねた予算管理を、三つの層で実装して比較した。

- L0：SDK の既定。`spendControls`（1回あたりの上限と、トークンの許可リスト）。
- L1：クライアントの方針。L0 に加えて、SDK のフックで「支払先の許可リスト」「タスクあたりの予算」「同じ URL の再購入禁止」「署名の有効期間の上限」を実装する。
- L2：オンチェーン。クライアント側では制御を行わない（SDK の制御も無効にする）。エージェントにはスマートウォレットの「セッション鍵」だけを渡し、ウォレットのコントラクトが制約を課す。クライアント側の制約が迂回された状況に相当する。

L1 は SDK のフック（`registerPolicy`と`onBeforePaymentCreation`）で実装した。

```ts
c.registerPolicy((_v, reqs) => reqs.filter(r => allowedPayees.has(r.payTo.toLowerCase())));
c.onBeforePaymentCreation(async ({ paymentRequired, selectedRequirements: r }) => {
  if (r.maxTimeoutSeconds > 600) return { abort: true, reason: "署名の有効期間が長すぎる" };
  if (bought.has(url))          return { abort: true, reason: "同じものを購入済み" };
  if (committed + BigInt(r.amount) > budget) return { abort: true, reason: "タスク予算超過" };
  committed += BigInt(r.amount);   // 署名した時点で使ったとみなす
  bought.add(url);
});
```

予算は、送金の確定時ではなく、署名の作成時に消費したものとして計上した。3.2 の D2 のとおり、署名は有効期限まで実行される可能性があるためである。

### EIP-1271 で支払い内容を検査する方法

EIP-1271 の`isValidSignature`が受け取るのは、32バイトのハッシュと署名だけである。ハッシュから宛先や金額は復元できない。

そこで、署名のバイト列に認可の内容を同梱させた。ウォレットは内容からハッシュを再計算し、渡されたハッシュと一致することを確認してから、内容を検査する。

```solidity
(Authorization memory a, bytes memory inner) = abi.decode(sig, (Authorization, bytes));
if (_digest(a) != hash)                          return INVALID; // 同梱された内容が署名対象と一致するか
if (!allowedPayee[a.to])                         return INVALID; // 支払先
if (a.value > maxPerPayment)                     return INVALID; // 1回の額
if (a.validBefore > block.timestamp + maxWindow) return INVALID; // 署名の有効期間
if (_recoverMem(hash, inner) != sessionKey)      return INVALID; // エージェントの鍵か
return MAGIC;
```

x402 の SDK は署名をバイト列のまま扱い、USDC の実装もそれを`isValidSignature`にそのまま渡す。そのため、この方式は SDK と USDC の実装を変更せずに動作した。

### 実験

同じ6つのシナリオを三つの層で実行した。各セルは支払った額（USDC）と、リクエストの結果である。

| シナリオ | L0 SDK既定 | L1 クライアント方針 | L2 オンチェーン |
| --- | --- | --- | --- |
| 1 正規の API に 0.01 | 0.01 | 0.01 | 0.01 |
| 2 未知の支払先（すり替えられた API） | 0.01 | 0（拒否） | 0（402） |
| 3 正規の支払先が 0.9 を要求 | 0.90 | 0.90 | 0（402） |
| 4 同じレポートを3回 | 0.03 | 0.01 | 0.03 |
| 5 0.3 を別々に6回 | 1.80 | 0.90（予算超過） | 0.90（残高不足） |
| 6 署名の有効期間 1年を要求 | 0.01 | 0（拒否） | 0（402） |

（L0 と L1 の1回の上限は 1 USDC、L2 は 0.5 USDC。L2 のウォレットには 1 USDC のみを入金した）

L0 の結果から、SDK の既定の制御が検査するのは1回の額とトークンの種類のみで、支払先、累積額、重複、署名の有効期間は検査しないことがわかる。サーバーが有効期間に1年を指定すると、1年間有効な署名が作成された。

L1 はシナリオ2・4・6を拒否し、シナリオ5を予算 1 USDC の範囲で止めた。シナリオ3が通ったのは、1回の上限を 1 USDC に設定していたためである。L1 の制約はエージェントと同じプロセス内で動作するため、鍵を持つプロセスが別の経路で署名すれば迂回できる。

L2 は、クライアント側の制御がない状態で、支払先・1回の額・署名の有効期間を強制した。セッション鍵が漏洩した場合も、支払いはこれらの制約の範囲に限られる。

### 累積額の制限

L2 でシナリオ5を止めたのは、ウォレットのコードによる検査ではなく、残高不足である。

対照実験として、`isValidSignature`の中で支払い回数を記録しようとするウォレットを実装した。結果は 402 で、記録は0回だった。トークンは`isValidSignature`を`staticcall`（状態を変更できない呼び出し）で呼ぶため、書き込みは失敗する。facilitator の署名検証は通過した。facilitator は`isValidSignature`を`eth_call`で直接呼び出しており、この呼び出しは書き込みを禁止しないためである。支払いを止めたのは、その後のシミュレーションだった。

EIP-3009 の送金経路には、ウォレットが自身の状態を更新する箇所がない。したがって、オンチェーンで強制できる累積の上限は、実質的にウォレットの残高になる。エージェントのウォレットには、予算として許容する額（例：1日分）だけを入金しておく構成が必要になる。

### 重複購入の検出

シナリオ4を止めたのは L1 のみである。オンチェーンのウォレットから見ると、3件の送金はそれぞれ条件を満たす別の支払いである。同じものを購入したかどうかは、購入の文脈を持つクライアントまたはアプリケーションの層でしか判定できない。

今回はエージェントを決定論的なプログラムで代用しており、LLM を接続した場合（例：ツールの応答が予算の上限の解除を指示する場合）の挙動は検証していない。L1 の制約はエージェントと同じプロセス内にあり、L2 の制約はコントラクトにある。LLM の出力がどちらの制約に影響しうるかは、エージェントの構成に依存する（未検証）。

## 5. それでも x402 は必要か

### ガス代の負担の移動

はじめにの疑問について、実験の範囲で確認できたことは次のとおりである。

ガス代の問題は解消されていた。ETH を持たないウォレットから支払えた。ただし、ガス代は facilitator の負担に移っており、第3章のとおり、失敗したトランザクションのガス代も facilitator が負担しうる。また売り手は、送金が確定する前に API の処理費用を負担している。

実験で実装と検証に手間を要した問題は、いずれもガス代とは関係がなかった。

- 応答が失われたときに、支払いの成否をどう確認するか
- 「同じ署名」ではなく「同じ購入」をどう識別するか
- 同時に届いたリクエストをどう1回に限定するか
- 受け付けなかった署名をどう無効にするか
- 支払ってよい相手、額、回数、期間を、どの層で保証するか

これらの多くは従来の決済 API にもある問題で、ブロックチェーンを使っても解決されない。また、署名が支払いを実行する能力を持つため、D2 のようなブロックチェーン固有の問題も加わる。

### 従来の決済手段と比べた x402 の性質

x402 には、従来の決済手段と異なる次の性質がある。いずれも本稿の実験では評価していない。

第一に、アカウントを作らずに購入できる。API キーの発行、契約、月次請求を経ずに、機械可読な価格を受け取り、その場で支払える。登録手続きを自ら行えないエージェントにとっては、この点が利点になる。

第二に、ブロックに取り込まれた送金は、決済事業者の判断で取り消されない。これは売り手にとっての利点であり、買い手にとってはチャージバック（支払いの取り消し）による救済がないことを意味する[要確認：各種カード決済のチャージバック制度との比較]。第4章でエージェントのウォレットに複数の制約を設けたのは、誤った支払いを取り消す手段がないためである。

一方で、利用者はウォレットの用意、USDC の入手、鍵の管理、支出制約の実装を行う必要がある。アカウント登録の手続きは、これらの準備に置き換わる。どちらの負担が小さいかは利用者によって異なる。

### 支払いの判断

AI エージェントが支払いを行う場合、価格の妥当性や支払先の信頼性を誰が判断するかが問題になる。SDK の既定の制御は、未知の支払先への支払いにも、1年間有効な署名の要求にも応じた。x402 が定めているのは支払いの手順であり、購入の適否の判断は定めていない。仕様は予算管理を implementation-specific としており、本稿の実験で実装の手間を要した部分の多くはこの範囲に含まれていた。

本稿の実験を通じて残った問いは、お金を動かす技術の進歩に比べて、お金を使う判断の難しさが扱われていないのではないか、というものである。これは結論ではない。

x402 は送金の部分を設計している。実験では、nonce は同じ署名の再利用を防ぎ、facilitator は宛先と金額を変更できず、settle の前には署名が再検証された。一方、署名が正しいこと、送金が成立すること、購入が適切に成立することの間にある差は、プロトコルの外側、すなわち売り手と買い手それぞれの実装で扱う必要がある。
