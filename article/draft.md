## はじめに

ブロックチェーンで送金するには、送金額とは別に「ガス代」がいる。ガス代はそのチェーンの基軸通貨（Ethereumなら ETH）で払う。だから、USDC[^usdc]を100ドル分持っていても、ETHを1円分も持っていなければ、その100ドルは動かせない。

この不便を解消する技術は、何年も前から積み重ねられてきた。署名だけで送金を承認し、ガス代は別の誰かが払う。メタトランザクション、EIP-2612、EIP-3009、Permit2。そして最近、その延長線上に **x402** が現れた。HTTPの`402 Payment Required`を使って、APIの呼び出しにその場でステーブルコインを払うプロトコルだ。「AIエージェントが自分で支払う」ための仕組みとして語られることも多い。

スマートコントラクトを書いてきた者として、私には一つ引っかかっていることがある。

**なぜ、ガス代を持たなくても支払えることに、こんなにも固執するのか。**

カードにも銀行振込にも、最初からガス代はない。ブロックチェーン固有の不便をブロックチェーン技術で解消することは、利用者にとっての前進ではあっても、決済にとっての前進とは限らない。決済の本当の難しさは、別のところにあるのではないか。

この記事では、この疑問を議論ではなくコードで確かめる。x402の公式SDKと、Circle が公開している USDC の実装コードをローカルのブロックチェーンに置き、まず一件支払う。次に、わざと壊す。署名を失効させ、応答を落とし、同時にリクエストを投げる。最後に、AIに持たせる財布を設計して、どこまでを強制できるかを測る。

見たいのは三つの区別だ。**署名が正しいこと。送金が成立すること。購入が適切に成立すること。** これらは、たぶん同じではない。

コードとログはすべて公開している（https://github.com/avcdsld/x402-techbook-lab）。本文に載せるのは、違いが現れる数行だけにする。

[^usdc]: 米ドルと価格が連動するように設計されたトークン（ステーブルコイン）の一つ。Circle 社が発行する。銀行預金そのものではない。

## 1. x402とは何か

### 402という空き番号

HTTPのステータスコード`402 Payment Required`は、長いあいだ「将来のために予約」とされてきた（RFC 9110 §15.5.3）。x402は、この空き番号に具体的な手順を与える。流れはこうなる。

```
クライアント                       リソースサーバー                facilitator
    │ GET /report                        │                               │
    │──────────────────────────────────▶│                               │
    │ 402  PAYMENT-REQUIRED: 支払い条件    │                               │
    │◀──────────────────────────────────│                               │
    │ （署名を作る）                       │                               │
    │ GET /report                        │                               │
    │ PAYMENT-SIGNATURE: 署名付きの支払い   │                               │
    │──────────────────────────────────▶│ verify ─────────────────────▶│
    │                                    │ settle ─────────────────────▶│──▶ ブロックチェーン
    │ 200  PAYMENT-RESPONSE: 決済結果      │                               │
    │◀──────────────────────────────────│                               │
```

登場人物は三者だ。

- **クライアント**：買い手。支払い条件を読み、署名を作る。
- **リソースサーバー**：売り手。APIそのもの。
- **facilitator**：署名を検証し（`verify`）、実際にブロックチェーンへ送金トランザクションを送る（`settle`）[^facilitator]。ガス代は facilitator が払う。

支払い条件は、たとえば「ネットワークは Base、トークンは USDC、金額は 10000（=0.01 USDC）、宛先はこのアドレス、署名の有効期間は60秒」といった JSON で、base64 にしてヘッダーに載る。

[^facilitator]: リソースサーバーが自分で facilitator を兼ねてもよい。仕様上は HTTP API として定義されている。

### 署名で送金する：EIP-3009

EVM系チェーンで x402 が既定で使うのは、EIP-3009 の`transferWithAuthorization`だ[^eip3009]。買い手は次の6項目に EIP-712 形式で署名する。

```
TransferWithAuthorization(
  address from, address to, uint256 value,
  uint256 validAfter, uint256 validBefore, bytes32 nonce
)
```

この署名を持っている人なら誰でも、トークンコントラクトに「この署名どおりに送金せよ」と頼める。ガス代を払うのは頼んだ人で、署名した人ではない。署名には宛先と金額が含まれているので、facilitator はそれを書き換えられない。`nonce`[^nonce]は一度使うと二度と使えないので、同じ署名で二回送金することもできない。

仕様（`scheme_exact_evm.md`）は facilitator の検証手順として、署名の検証、残高、金額と有効期間、トークンとネットワークの一致、そして送金のシミュレーションを挙げている。

[^eip3009]: ERC-20 トークンに「署名による送金」を追加する規格。USDC が実装している。x402 は他に Permit2、ERC-7710 による方式も定義しているが、本稿では扱わない。
[^nonce]: 署名付きの操作を一度きりにするための識別値。EIP-3009 では32バイトの乱数を使う。

### なぜ注目されるのか

x402 の仕様書には「AI Agent Integration」という節がある。エージェントが自律的にリソースへ支払えること、そして予算管理と支出制御が挙げられている。ただし括弧書きで、こう添えられている。

> **Budget management** and spending controls (implementation-specific)

予算管理は実装次第。この括弧の中身を、第4章で実際に埋めてみる。

## 2. まず支払ってみる

### 実験環境

壊す前に、まず一件、本物の部品で通す。

| 部品 | 使ったもの |
| --- | --- |
| ブロックチェーン | anvil（Foundry のローカルEVM） |
| トークン | Circle の `stablecoin-evm` に含まれる **FiatTokenV2_2**（USDC の実装）をソースからコンパイル |
| x402 | 公式 SDK `@x402/core` `evm` `express` `fetch` **2.28.0**（無改造） |

USDC はプロキシを介さず、実装コントラクトを直接デプロイした。送金と署名検証のロジックは本番と同じソースだ。facilitator は公式の`x402Facilitator`をリソースサーバーと同じプロセスで呼んでいる。間に挟んだのは、ログと故障注入のための薄い層だけだ。

### 売り手と買い手

売り手のコードは、ルートに値段を付けるだけで済む。

```ts
app.use(paymentMiddleware({
  "GET /report": {
    accepts: [{
      scheme: "exact",
      network: "eip155:31337",
      payTo: seller,
      price: { amount: "10000", asset: usdc, extra: { name: "USD Coin", version: "2" } },
      maxTimeoutSeconds: 120,
    }],
  },
}, resourceServer));

app.get("/report", (req, res) => res.json({ report: "..." }));
```

買い手は`fetch`を包むだけだ。

```ts
const client = new x402Client().register("eip155:*", new ExactEvmScheme(buyer));
const payFetch = wrapFetchWithPayment(fetch, client);
const res = await payFetch(`${url}/report`);
```

### 一件目

実行すると、次のログが出る（抜粋）。

```
[186ms] server       ← GET /report               (支払いなし)
[189ms] server       → HTTP 402
[198ms] client       署名を作成 nonce=0x241b…  value=10000
[200ms] server       ← GET /report               (支払いあり)
[213ms] facilitator  verify  isValid=true
[214ms] server       handler 実行
[230ms] facilitator  settle  success=true tx=0x02ea…
[231ms] server       → HTTP 200
```

買い手の残高は 0.01 USDC 減り、売り手は 0.01 USDC 増えた。nonce は使用済みになり、トランザクションの送信者は facilitator だった。後の実験では、**ETH を1 wei も持たないコントラクトウォレット**からも支払えた。ガス代なしで支払える、という約束は、この範囲では確かに果たされている。

このログで気になるのは、`handler 実行`が`settle`より前にあることだ。公式の Express ミドルウェアは、検証が通るとまず API の処理を実行する。応答は送らずに手元に溜めておき、決済が確定してから送る。決済が失敗したら、溜めた応答は捨てて 402 を返す。

つまり、**サービスは送金の確定より先に提供される**。本文は渡さないので、買い手がただで得をすることはない。けれども、計算資源は使われ、外部の API を呼んでいればその費用も発生する。

もう一つ、つまずいたことがある。最初の実行は 402 を受け取った直後にクライアント側で止まった。

```
All payment requirements were rejected by spendControls: only default assets
or entries in spendControls.allowedAssets are allowed.
```

SDK のクライアントは既定で、SDK が知らないトークンへの支払いを拒否する。ローカルに置いた USDC は知らないトークンなので、明示的に許可する必要があった。支出の制御は、最初の一歩から顔を出している。この話は第4章で続ける。

検証が通り、API が実行され、そのあとで送金する。では、**検証と送金のあいだに何かが変わったら**どうなるのか。

## 3. 決済を壊してみる

### 3.1 署名は正しいのに、支払えない

#### 状態に依存する署名

普通のアカウント（EOA[^eoa]）の署名は、暗号学的に検証できる。署名とメッセージがあれば、誰が署名したかは数学的に決まり、時間が経っても変わらない。

一方、コントラクトでできたウォレット（スマートウォレット）には秘密鍵がない。そこで EIP-1271[^1271] では、ウォレット自身に「この署名は有効か」を答えさせる。

```solidity
function isValidSignature(bytes32 hash, bytes calldata sig) external view returns (bytes4) {
    return _recover(hash, sig) == owner ? MAGIC : INVALID;
}

function rotateOwner(address next) external {
    require(msg.sender == owner, "not owner");
    owner = next;
}
```

実験用に書いたウォレットの全てだ。署名が有効かどうかは「**いまの** owner が署名したか」で決まる。だから鍵をローテーションすると、過去に出した署名はすべて無効になる。

これは私の工夫ではない。USDC の実装自体が、署名検証ライブラリのコメントでこう書いている。

> NOTE: Unlike ECDSA signatures, contract signatures are revocable, and the outcome of this function can thus change through time. It could return true at block N and false at block N+1 (or the opposite).
> （`contracts/util/SignatureChecker.sol`）

ブロックNで有効だった署名が、ブロックN+1では無効になりうる。x402 の`verify`と`settle`のあいだには、少なくとも API の実行時間ぶんの隔たりがある。

[^eoa]: Externally Owned Account。秘密鍵で直接操作する、普通の Ethereum アカウント。
[^1271]: スマートコントラクトが、署名の有効性を問い合わせに応じて回答するための規格。

#### 実験

facilitator の`settle`の直前にフックを挟み、そこで署名を失効させた。比較のため、EOA でも同様のことを試した。EOA の場合は、EIP-3009 に定義されている`cancelAuthorization`（nonce を先に使用済みにする）を使う。

| ケース | HTTP | API実行 | 送金 | facilitator の tx | facilitator のガス代 |
| --- | --- | --- | --- | --- | --- |
| A 1271・何もしない | 200 | 1 | 0.01 | 1 | 0.000101 ETH |
| B 1271・verify後に owner 交代 | 402 | 1 | 0 | 0 | 0 |
| C EOA・verify後に `cancelAuthorization` | 402 | 1 | 0 | 0 | 0 |
| D 1271・settle の tx 送信**後**に owner 交代 | 402 | 1 | 0 | 1（失敗） | **0.000052 ETH** |
| E EOA・settle の tx 送信**後**に `cancelAuthorization` | 402 | 1 | 0 | 1（失敗） | **0.000034 ETH** |

（ガス代は anvil 上の値。絶対値に意味はなく、比較のために載せている）

B は、SDK が`settle`の前に**署名を検証し直す**ことで止まった。SDK の検証は、コードを持つアドレスに対しては必ずオンチェーンの`isValidSignature`を呼ぶ。トランザクションは送られず、facilitator は何も失っていない。

C を止めたのは、SDK の明示的な検査ではなかった。`settle`前の再検証では、送金のシミュレーションは**既定で無効**だ（`simulateInSettle: false`）。実際に止めたのは、トランザクションを送る直前に viem（Ethereum クライアントライブラリ）が行う**ガス見積り**だった。見積りの段階で送金が revert することがわかり、送信が中止された。安全装置が、意図された場所とは別の場所で働いている。

D と E は、facilitator がトランザクションを送った**後に**、より高い手数料をつけた失効のトランザクションを割り込ませたケースだ。採掘されたブロックでは、失効が先、送金が後に並んだ。

```
[834ms] facilitator  settle tx を送信 0xdd5d…
[839ms] wallet       より高いチップで owner 交代 tx を投入
[856ms] chain        1ブロック採掘 order=[owner交代, settle]
[858ms] facilitator  settle success=false reason=transaction_failed
```

送金は revert し、facilitator はガス代だけを払った。

#### 何がわかったか

まず、**これは EIP-1271 固有の問題ではない**。EOA でも`cancelAuthorization`で同じことが起きる（C・E）。残高を別のアドレスに移すだけでもいい。署名が正しくても、送金の時点で払えるとは限らない。それは署名の性質ではなく、検証と実行が別の時刻に行われることの帰結だ。

EIP-1271 で違うのは、失効が**正当な運用として**起きうることだ。鍵のローテーションは、セキュリティ上むしろ推奨される操作だ。その操作が、未決済の支払いをすべて無効にする。

次に、被害者は誰か。D と E で得をした人はいない。買い手は本文を受け取っていない。損をしたのは、API を実行した売り手（計算資源）と、ガス代を払った facilitator だ。これを「攻撃」と呼ぶなら、買い手が自分の支払いを取り消すことで、他者に小さな費用を負わせる攻撃ということになる。x402 の仕様は、ERC-7710 方式の節で、この競合を facilitator のリスクとして明記している。EIP-3009 方式の節には同種の記述はないが、今回の実験では EIP-3009 でも起きた。

そしてもう一つ。**検証を通った支払いは、将来も支払えることを意味しない**。サービスを先に提供する以上、検証から送金までの隔たりのリスクは、売り手側が負う。

### 3.2 同じものに二度払う

#### GET は安全。でも財布は？

HTTP の GET は「安全な」メソッドだとされる。クライアントはサーバーの状態を変えることを要求していない、という意味だ（RFC 9110 §9.2.1）。そして冪等でもある。同じリクエストを何度送っても、意図される効果は同じだ。だからブラウザやライブラリは、通信が切れた GET を気軽に再送する。

x402 では、GET の向こうで送金が起きる。

次の状況を考える。買い手が支払い、送金はブロックチェーン上で確定した。ところが、その直後に通信が切れ、成功の応答が買い手に届かなかった。買い手から見ると、払ったのかどうかがわからない。

これを再現するために、settle が成功した後の応答を送る瞬間に、TCP 接続ごと切った。

```ts
res.end = (...args) => {
  if (dropResponse.on && res.statusCode === 200) {
    dropResponse.on = false;
    req.socket.destroy();   // 決済は済んだ。応答だけが消える
    return res;
  }
  return end(...args);
};
```

#### 実験

A〜F は、最初の決済の直後に応答を一度だけ落とした。G〜I は応答を落とさず、同じ購入を同時に二回送った。

| | 重複防止 | 再試行のしかた | 最終応答 | 支払い | API実行 |
| --- | --- | --- | --- | --- | --- |
| A | なし | SDK で再リクエスト | 200 | **2** | 2 |
| B | なし | 同じ署名を再送 | **402** | 1 | 1 |
| C | `payment-identifier` | 同じ署名を再送 | 200 | 1 | 1 |
| D | `payment-identifier` | 同じ id で SDK 再リクエスト | **409** | 1 | 1 |
| D2 | 〃 | D の後、断られた署名を売り手が実行 | — | **2** | 1 |
| E | `payment-identifier` | 再起動して id も作り直す | 200 | **2** | 2 |
| F | アプリの購入 ID | 再起動して同じ購入 ID で再リクエスト | 200 | 1 | 1 |
| G | アプリの購入 ID | 同時に二回 | 200/200 | **2** | 2 |
| I | 購入 ID ＋処理中の予約 | 同時に二回 | 409/200 | 1 | 1 |

順に見ていく。

**A：素直に再試行すると、二回払う。** SDK でもう一度リクエストすると、サーバーはまた 402 を返す。SDK は新しい nonce で新しい署名を作る。新しい署名は別の送金なので、nonce は何も防がない。

**B：同じ署名を再送すると、払ったのに何も受け取れない。** nonce はすでに使用済みなので、検証で落ちて 402 になる。二重払いは防げたが、買い手の手元には何もない。

nonce が防ぐのは「同じ署名の再利用」であって、「同じ購入の繰り返し」ではない。署名の同一性と、購入の同一性は別物だ。

**C・D：公式の冪等性拡張。** x402 には`payment-identifier`という拡張がある。クライアントが支払いに ID を付け、再試行では同じ ID を使う。ただし、SDK が提供するのは ID の宣言と抽出の関数だけで、重複を判定する仕組みは実装者に任されている。ソースにはこう書かれている。

```ts
// No enrichment needed - the declaration is static
// Future hooks for idempotency could be added here if needed
```

公式のサンプルサーバーは、ID と、**署名を含むペイロード全体**の指紋（ハッシュ）を記録する。同じ署名で再送すれば、記録済みの結果を返す（C）。同じ ID で新しい署名を送ると、「同じ ID で違う内容」として 409 を返す（D）。二重払いは防げる。ただ D の買い手は、やはり何も受け取れない。

**D2：断られた署名は、まだ生きている。** D で 409 を返されたリクエストにも、署名は付いていた。その署名は未使用で、有効期限（`validBefore`）まで有効だ。売り手側でそれを`transferWithAuthorization`に渡すと、送金は成功した。

署名付きの送金承認は、受け取った人が期限内ならいつでも換金できる、持参人払いの小切手に近い。サーバーが「受け付けない」と答えても、小切手はサーバーの手元に残る。期限は、サーバーが支払い条件の`maxTimeoutSeconds`で指定する。

**F：購入の同一性は、アプリの層にしかない。** 支払いより前に、アプリ側の購入 ID（たとえば注文番号）を、認証済みの買い手と結びつけて照合する。購入済みなら、支払いを求めずに同じ結果を返す。こうすれば、クライアントが再起動して署名を作り直しても、支払いは一回で済む。

**G・I：同時に来たら。** F の実装には穴がある。同じ購入 ID のリクエストが同時に二つ来ると、どちらも「まだ購入されていない」と判定されて通過し、二回払いになる（G）。処理中の購入 ID を予約しておき、二つ目を 409 で断ると解消する（I）。

ただし I でも、断られた側のクライアントは、402 を受け取った時点ですでに署名を作っていた。予約より前に署名が生まれる順序は、このプロトコルの形から来ている。

#### これはブロックチェーンの問題か

G と I で起きたことは、従来の決済 API でもまったく同じように起きる。だから Stripe などの決済 API は、`Idempotency-Key`ヘッダーで再試行を識別する仕組みを持っている[要確認：Stripe の idempotency key の仕様、同時リクエスト時の挙動]。応答が失われたときに「払ったのかどうか」を確かめ、購入を一度きりにする責任は、どの決済手段でもアプリケーションに残る。

ブロックチェーン固有なのは、D2 のほうだ。決済事業者のサーバーではなく署名そのものが支払い能力を持つので、断られたリクエストの残骸がそのまま支払い手段として残る。

副産物も記録しておく。素の viem で送金トランザクションを送る facilitator（公式の facilitator サンプルと同じ構成）は、二つの`settle`を同時に処理すると送信アカウントの nonce が衝突した（`nonce too low`）。この実験では、それが偶然二重払いを防いだ。代わりに API は二回実行され、片方の買い手は 402 を受け取った。ガス代を肩代わりする facilitator は、送金を一つのアカウントから直列に送り出す、混雑する窓口でもある。

## 4. AIの財布を設計する

### 支払えることと、支払ってよいこと

x402 は「支払える」ことを可能にする。けれども、AI が**支払ってよいかどうか**は決めてくれない。仕様が「実装次第」とした予算管理を、三つの層で実装して比べた。

- **L0：SDK の既定。** `spendControls`（1回あたりの上限と、トークンの許可リスト）。
- **L1：クライアントの方針。** L0 に加えて、SDK のフックで「支払先の許可リスト」「タスクあたりの予算」「同じ URL の再購入禁止」「署名の有効期間の上限」を足す。
- **L2：オンチェーン。** クライアント側は何もしない（SDK の制御も切る）。エージェントにはスマートウォレットの「セッション鍵」だけを渡し、ウォレットのコントラクトが制約を課す。クライアント側の制約が迂回された状況に相当する。

L1 は、SDK のフックに素直に書ける。

```ts
c.registerPolicy((_v, reqs) => reqs.filter(r => allowedPayees.has(r.payTo.toLowerCase())));
c.onBeforePaymentCreation(async ({ paymentRequired, selectedRequirements: r }) => {
  if (r.maxTimeoutSeconds > 600) return { abort: true, reason: "署名の有効期間が長すぎる" };
  if (bought.has(url))          return { abort: true, reason: "同じものを購入済み" };
  if (committed + BigInt(r.amount) > budget) return { abort: true, reason: "タスク予算超過" };
  committed += BigInt(r.amount);   // 署名した時点で使ったとみなす
  bought.add(url);
});
```

予算は、送金が確定した時点ではなく、**署名した時点**で消費したとみなした。3.2 の D2 で見たとおり、署名は期限まで換金されうるからだ。

### 32バイトしか見えない

L2 は簡単ではない。EIP-1271 の`isValidSignature`が受け取るのは、32バイトのハッシュと署名だけだ。ハッシュからは、宛先も金額も復元できない。

そこで、署名のバイト列に認可の中身そのものを同梱させた。ウォレットは中身からハッシュを計算し直し、渡されたハッシュと一致することを確かめてから、中身を検査する。

```solidity
(Authorization memory a, bytes memory inner) = abi.decode(sig, (Authorization, bytes));
if (_digest(a) != hash)                          return INVALID; // 中身は本物か
if (!allowedPayee[a.to])                         return INVALID; // 支払先
if (a.value > maxPerPayment)                     return INVALID; // 1回の額
if (a.validBefore > block.timestamp + maxWindow) return INVALID; // 署名の寿命
if (_recoverMem(hash, inner) != sessionKey)      return INVALID; // エージェントの鍵か
return MAGIC;
```

x402 の SDK は署名をただのバイト列として運ぶ。USDC の実装もそれを`isValidSignature`にそのまま渡す。だからこの細工は、SDK にも USDC にも手を入れずに動いた。

### 実験

同じ6つのシナリオを三つの層で実行した。セルは支払った額と、各リクエストの結果だ。

| シナリオ | L0 SDK既定 | L1 クライアント方針 | L2 オンチェーン |
| --- | --- | --- | --- |
| 1 正規の API に 0.01 | 0.01 | 0.01 | 0.01 |
| 2 知らない支払先（すり替えられた API） | **0.01** | 0（拒否） | 0（402） |
| 3 正規の支払先が 0.9 を要求 | 0.90 | 0.90 | 0（402） |
| 4 同じレポートを3回 | 0.03 | 0.01 | **0.03** |
| 5 0.3 を別々に6回 | **1.80** | 0.90（予算切れ） | 0.90（残高切れ） |
| 6 署名の有効期間 1年を要求 | **0.01** | 0（拒否） | 0（402） |

（L1 と L0 の1回の上限は 1 USDC、L2 は 0.5 USDC。L2 のウォレットには 1 USDC だけを入れた）

L0 の列が示すとおり、SDK の既定が見ているのは「1回の額」と「トークンの種類」だけだ。**支払先も、累積額も、重複も、署名の寿命も見ていない**。サーバーが有効期間に1年を指定すれば、1年有効な署名がそのまま作られる。

L1 は、すべて止めた（3 が通ったのは上限を 1 USDC に設定したため）。ただし、L1 の制約はエージェントと同じプロセスの中で動くコードだ。鍵を持つプロセスが別の経路で署名すれば、迂回できる。

L2 は、クライアントが何もしなくても、支払先・額・寿命を強制した。セッション鍵が漏れても、被害はこの範囲に収まる。

### 数えられない累積

では、累積の予算はどうか。L2 のシナリオ5を止めたのは、私が書いた検査ではない。ウォレットの残高が尽きたのだ。

対照実験として、`isValidSignature`の中で支払い回数を記録しようとするウォレットを書いた。結果は 402 で、記録は0回だった。トークンは`isValidSignature`を`staticcall`（状態を変えられない呼び出し）で呼ぶので、書き込みは失敗する。興味深いことに、facilitator の署名検証そのものは通った。facilitator は`isValidSignature`を`eth_call`で直接呼んでおり、こちらは書き込みを禁じないからだ。止めたのは、その後のシミュレーションだった。

EIP-3009 の送金経路には、ウォレットが自分の状態を更新できる場所がない。だからオンチェーンで強制できる累積の上限は、事実上「**残高**」になる。エージェントの財布に1日分の予算だけを入れておく。最も確実な支出上限は、それ以上を持たせないことだった。プリペイドカードと同じ発想だ。

### 誰も知らない「同じもの」

シナリオ4（同じレポートを3回）を止められたのは、L1 だけだった。オンチェーンのウォレットにとって、三つの送金はそれぞれ正当な、別々の支払いだ。「同じものを買った」という意味は、購入の文脈を知るクライアントかアプリケーションの層にしか存在しない。

今回は、エージェントを決定論的なプログラムで代用した。LLM をつないだとき、たとえばツールの応答が「予算の上限を外せ」と書いてきた場合に何が起きるかは試していない。ただ、表の L1 と L2 の違いは、その問いにも一つの示唆を与える。言葉で説得できる場所にある制約と、そうでない場所にある制約がある。

## 5. それでも x402 は必要か

### ガス代は、どこへ行ったか

出発点の問いに戻る。ガス代を持たなくても支払えることは、決済の中心的なハードルなのか。

実験の範囲で言えば、ガス代の問題は確かに解かれていた。ETH を持たないウォレットから支払えた。ただし、ガス代は消えたのではなく、facilitator に移っていた。そして第3章で見たとおり、facilitator は失敗したトランザクションのガス代も負担しうる。売り手は、送金が確定する前に API の原価を払っている。

それ以上に、実験で手間がかかったのは、どれもガス代とは関係のない問題だった。

- 応答が失われたとき、払ったのかどうかをどう確かめるか
- 「同じ署名」ではなく「同じ購入」をどう識別するか
- 同時に来たリクエストをどう一度きりにするか
- 受け付けなかった署名を、どう無害にするか
- 支払ってよい相手、額、回数、期間を、どの層で保証するか

これらのほとんどは、従来の決済 API にもある問題だ。ブロックチェーンは、これらを解いてくれない。署名が支払い能力そのものである分、D2 のような新しい形で問題を持ち込みさえする。

### 固有の価値があるとしたら

それでも、x402 にしかない性質はある。

一つは、**アカウントを作らずに買える**ことだ。API キーの発行、契約、月次請求を経ずに、未知の API へ、その場で、機械可読な価格で支払える。人間が登録画面を通れないエージェントにとって、これは小さくない。

もう一つは、送金の**確定性**だ。ブロックに入った送金は、決済事業者の判断で巻き戻らない。これは売り手にとっての利点で、裏返せば、買い手にとってはチャージバック（支払いの取り消し）による救済がないことを意味する[要確認：各種カード決済のチャージバック制度との比較]。第4章でエージェントの財布にあれほど制約を重ねたのは、間違って払ったら戻ってこないからだ。

ただし、アカウント不要という利点の裏で、利用者はウォレットを用意し、USDC を入手し、鍵を管理し、支出の制約を自分で書く必要がある。アカウント登録の手間は、消えたというより、別の形の準備に置き換わっている。どちらが軽いかは、誰が使うかによる。

### 支払う能力と、買う判断

AI が自由に払えるようになったとき、価格が妥当か、相手が信用できるかを判断するのは誰か。SDK の既定は、知らない支払先へのリクエストにも、1年有効な署名の要求にも応じた。x402 が標準化したのは「支払う能力」であって、「適切に買う判断」ではない。仕様が予算管理を「実装次第」とした括弧の中には、決済のいちばん難しい部分が入っていたことになる。

私たちは、お金を動かす技術ばかり進歩させて、お金を使うことの難しさを見落としていないだろうか。

これは結論ではなく、実験を終えて残った問いだ。x402 は、お金を動かす部分をよく設計している。nonce は同じ署名の再利用を確実に防いだ。facilitator は宛先も金額も書き換えられなかった。settle の前には署名が検証し直された。けれども、署名が正しいこと、送金が成立すること、購入が適切に成立することのあいだの隔たりは、プロトコルの外側、売り手と買い手それぞれのコードに残されている。その隔たりを埋めるコードを書くことが、たぶん、これからの「決済」の仕事だ。

## 付録：実験の範囲

**使ったもの**：x402 仕様・SDK ソース `x402-foundation/x402@faa1c694`、npm `@x402/*@2.28.0`、viem 2.57.7、Circle `stablecoin-evm@fc85788` の FiatTokenV2_2、Foundry 1.7.1（anvil）、solc 0.6.12 / 0.8.30、Node.js 22.22.0。

**本物と違うところ**：USDC はプロキシなしで直接デプロイした。facilitator は HTTP で分離せず同一プロセスで動かした。ウォレットの署名形式は簡略化してある（実在のスマートウォレットはハッシュを包み直す）。anvil に Multicall3 がないため、SDK の失敗原因の診断が働かず、一部のエラー理由が汎用的なものになった。

**やっていないこと**：テストネット・本番ネットワーク、Permit2 / ERC-7710 方式、EIP-7702、LLM を接続したエージェント、`simulateInSettle: true`の場合の挙動、従来の決済 API との実測による比較。
